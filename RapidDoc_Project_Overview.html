Executive Summary

What RapidDoc is and the fundamental technical problem it solves
⚠️

The "LLM Document Problem" (Why Traditional AI Fails)

If you upload a Microsoft Word (.docx) or PDF document to ChatGPT, Claude, or Gemini and ask it to "make all headings blue" or "replace the author name", the LLM will dump back plain text or raw markdown.

  • Layout Destruction: Embedded tables, fonts, header/footer links, and margins are wiped out.
  • Media Loss: Corporate logos, figures, and charts vanish completely.
  • Unverifiable Hallucination: An LLM might change numbers, dates, or rewrite unrelated paragraphs without notice.
💡

The RapidDoc Solution (Separation of NLU & Execution)

RapidDoc strictly separates Natural Language Understanding (NLU) from Document DOM Execution.

  • AI acts only as a Parser: The AI identifies the Intent (e.g. replace_text) and extracts the Slots (e.g. old_text="Draft", new_text="Final").
  • Deterministic Code Modifies the File: A low-level OpenXML/DOM engine modifies the exact XML nodes, preserving 100% of the fonts, tables, styles, headers, and media.
  • Yellow Run Highlights: Edits are highlighted in yellow so the user can see exactly what changed before accepting.
🎯 Core Value Proposition

RapidDoc gives users the convenience of talking to their documents in conversational English (e.g., "Change footer to 'Page {PAGE}'", "Summarize Section 2", "Make 5 MCQs for student revision", "Export as Modern PowerPoint") while guaranteeing that the underlying document remains an authentic, professional, formatting-preserved Word or PDF document.

The 3-Tier AI Cascade & "Dual Brain" Hybrid Architecture

Why RapidDoc uses three cascading layers instead of relying solely on an external API
💻
Tier 1: Primary Engine

Local Fine-Tuned Models

Four specialized lightweight transformer models running directly on CPU (or GPU) using HuggingFace & PyTorch.

  • Intent Model: distilbert-base-uncased fine-tuned on 8,400 examples across 24 intents.
  • Text Rewriter: T5-small trained on the Grammarly CoEdIT dataset.
  • MCQ Generator: BART-base fine-tuned on the RACE reading dataset.
  • Summarizer: BART-large-cnn complete-document pipeline.
  • Benefits: Zero API bills, zero internet dependency, completely private.
☁️
Tier 2: Intelligent Fallback

Google Gemini 3.8 Flash

Triggered automatically when the local intent confidence is below INTENT_CONFIDENCE_THRESHOLD (0.15) or for ambiguous inputs.

  • Role: Translates conversational, complex, or colloquial prompts into structured JSON.
  • Output: Returns standardized action payloads ({"action": "replace", "find_text": "...", "replace_text": "..."}).
  • Safety: Still never writes to the document directly; it only provides instructions to the deterministic engine.
🛡️
Tier 3: Absolute Fail-Safe

Deterministic Regex Engine

Hard-coded heuristic rule patterns that run if both local models and cloud APIs fail (e.g., offline with no weights).

  • Patterns: Regexes for FALLBACK_HEADER_RE, replace syntax, and common formatting verbs.
  • Guaranteed Uptime: Ensures core features (changing headers, find-and-replace, page setup) work 100% of the time.
  • Zero Crashes: The application never throws a 500 error due to AI model downtime.
🔒 Thread Safety & Concurrency Control in Local Models

Inside local_models.py, inference is guarded by a recursive lock (_INFER_LOCK) and model loading is protected by _LOAD_LOCK. Because PyTorch on CPU already saturates all available CPU cores with multi-threaded BLAS operations, serializing inference per request eliminates race conditions, prevents memory thrashing, and guarantees reproducible results without slowing down server throughput.

The Six Core System Modules

Deep dive into the modular responsibilities of the RapidDoc backend
Module 1 Document Ingestion & Multi-Format Reconstruction Engine
▼

Primary Files: docx_editor.py, pdf_editor.py, pdf_converter.py, export_service.py

Parses multi-format input documents into an internal canonical tree representation (the python-docx Document Object Model) and handles clean serialization on export.

Supported Ingestion Formats

  • .docx: Direct structured XML parsing via python-docx.
  • .pdf: Text runs, font sizes, bounding boxes via PyMuPDF (fitz) and pdfplumber.
  • .txt: Normalized into paragraph blocks.
  • .pptx: Outlines and slides parsed via python-pptx.

Export Pipeline

  • Native DOCX and TXT serialization.
  • Headless LibreOffice integration (soffice --headless --convert-to pdf) for pixel-perfect PDF rendering with all styling and embedded fonts preserved.
Module 2 NLU & Intent Classification Router
▼

Primary Files: slot_extractor.py, gemini_service.py, local_models.py

Maps arbitrary user natural language instructions to an unambiguous structured JSON payload. 

{
  "intent": "replace_text",
  "confidence": 0.985,
  "slots": {
    "old_text": "Draft v2",
    "new_text": "Final Submission",
    "page": null
  }
}

The slot extractor uses deterministic entity parsing to capture parameters like page, old_text, new_text, font_name, font_size, color, and alignment without hallucinating values that were not in the user's prompt (the Phantom Slot Fix).

Module 3 Deterministic Document Execution Engine
▼

Primary Files: docx_editor.py, header_footer.py, image_geometry.py

Manipulates OpenXML nodes directly to guarantee zero hallucinations and format preservation.

🔍 The "Cross-Run Text Fragmentation" Problem & Solution

In Microsoft Word XML, a sentence like "Hello World" is rarely stored as a single string. It is often split across multiple <w:r><w:t>Hello </w:t></w:r><w:r><w:t>World</w:t></w:r> run tags due to spellchecking or past edits. If you do a simple string replace on individual runs, the match fails!

RapidDoc's Solution: docx_editor.py implements a run-coalescing algorithm that combines text across run boundaries, performs the match, injects the replacement, and preserves adjacent formatting while tagging replaced runs with <w:highlight w:val="yellow"/> for visual diffing.

Module 4 Local Neural Generation Engine (Seq2Seq Tasks)
▼

Primary Files: local_models.py, mcq_generator.py, text_polish.py

Executes targeted text transformations and educational generation using locally hosted Seq2Seq transformer models.

  • Targeted Text Rewriter: Fine-tuned T5-small on the grammarly/coedit dataset (69k records). Understands instructions like "make formal:", "fix grammar:", "simplify:".
  • Educational Assessment Generator: Fine-tuned BART-base on the ehovy/race dataset (20k records). Generates 4-option multiple choice questions, plausible distractors, answer keys, explanations, flashcards, and viva examination questions.
  • Beam Candidate Validation: Evaluates top 4 candidates from a single beam search tree, discarding malformed records and returning only valid questions.
Module 5 Pretrained & Unsupervised Document Analytics Engine
▼

Primary Files: document_summarizer.py, document_text.py, summary_export.py

Provides fast, offline document summarization, keyword extraction, and translation.

📑 Map-Reduce Long-Document Summarization with Late-Section Retention

Standard BART models have a 1,024-token context window. Most document summarizers naively truncate after page 2, completely omitting conclusions, results, and recommendations!

RapidDoc's Solution: 1. Complete Text Extraction & Cleaning (preserving metrics and numbers via regex).
2. Heading & Boundary Detection (Abstract, Methodology, Results, Conclusion).
3. Map Phase: Summarizes each section chunk individually.
4. Reduce Phase: Synthesizes section summaries into a master executive summary.
5. Late-Section Retention: Guarantees terminal sections (Conclusions & Discussion) are weighted and included in the final output.

Module 6 Backend Orchestration, Session Store & Presentation Engine
▼

Primary Files: main.py, database.py, version_history.py, ppt_templates.py, storage.py

Orchestrates sessions, state persistence, PowerPoint template generation, and version rollbacks.

  • Session & Version History: 40-step snapshot timeline. Copies the raw document binary to disk before applying any mutation, allowing instant one-click rollback.
  • Presentation Engine (PPTX): Uses an outline builder to turn document headings and table labels into branded PowerPoint slides with three themes (Modern, Corporate, Minimal) and overflow control (max 7 bullets, max 14 table rows per slide).
  • MongoDB Persistence: Stores document metadata, ownership, pipeline progress stages (1: Ingested, 2: Header/Footer, 3: Content Editing, 4: Finalized), and user auth profiles.

End-to-End Data Flow & Lifecycle

What happens when a user types a command? Step-by-step trace
🔄 Example Scenario: User types "Replace 'Confidential Draft' with 'Approved Version' and change font to Arial"
  1. Step 1 (UI Capture): User enters prompt in DocumentWorkspace.jsx and clicks Send. Request is sent to POST /api/v1/documents/{doc_id}/ai-command with JWT auth header.
  2. Step 2 (Snapshot Guard): version_history.py creates a physical binary copy of the current file in backend/storage/v{n}.docx before any changes occur.
  3. Step 3 (NLU Cascade Routing):
    • Calls classify_intent() on local DistilBERT model. Confidence = 0.98 ➔ Intent = replace_text.
    • Calls extract_slots() ➔ Extracts old_text="Confidential Draft", new_text="Approved Version", font_name="Arial".
    • (If confidence was < 0.15, it would fall back to Google Gemini gemini-3.8-flash or Regex).
  4. Step 4 (Deterministic DOM Execution):
    • docx_editor.py opens the document OXML package.
    • Runs cross-run coalescing across all paragraphs and table cells to match "Confidential Draft".
    • Replaces text, updates the run's font to Arial, and appends <w:highlight w:val="yellow"/>.
    • Saves the updated document to backend/storage/{doc_id}.docx.
  5. Step 5 (Diff & Metadata Update): MongoDB document record is updated with the edit entry (timestamp, action, user).
  6. Step 6 (UI Refresh): Backend returns HTTP 200 with changed blocks. Frontend updates preview pane showing yellow highlighted modifications with an option to Accept or Revert.

Model Training, Datasets & Evaluation

How RapidDoc's AI models were constructed, trained, and benchmarked

Dataset Engineering (generate_dataset.py)

To train the intent classifier, 8,400 schema-validated records were generated across 24 intent categories (exactly 280 examples each) to prevent class imbalance.

  • Train / Val / Test Split: 80% train (6,720), 10% val (840), 10% test (840).
  • The "Phantom Slot" Innovation: In earlier synthetic datasets, templates included slots like page=2 even when the sentence didn't say it. RapidDoc only registers slots that explicitly appear in the generated text, eliminating hallucinated slot predictions.
  • Politeness & Framing Diversity: Uses prefixes ("please", "kindly", "could you") and generic frames to create 300+ unique sentence structures per intent.

Task Datasets & Pretrained Checkpoints

RapidDoc leverages domain-specific datasets rather than general-purpose conversational LLMs:

  • CoEdIT (Grammarly): 69,000 instruction-guided text rewriting pairs used for tone changes, simplification, and grammar repair.
  • RACE (Reading Comprehension): 20,000 multi-choice comprehension questions with distractors used for fine-tuning BART-base.
  • CNN / DailyMail: Evaluated for abstractive summarization metrics.

Viva & Reviewer Q&A: Master Cheat Sheet

Top 10 questions examiners, interviewers, or reviewers will ask you — and the exact answers to give
Q1 Why not just copy-paste the document text into ChatGPT or Gemini and let it rewrite the document?
LLMs are purely text-to-text token predictors; they have no concept of OpenXML document hierarchies, binary zip structures, or PDF coordinate trees. If you give an LLM a Word document, it strips out embedded tables, multi-section headers, footer unlinking, page numbers, dynamic field codes, and embedded images. You get back plain text or raw markdown.

RapidDoc's approach: AI is only used for natural language comprehension (determining intent and slots). The actual document modification is performed by a deterministic XML/DOM engine, which guarantees zero loss of styling, formatting, tables, or media.
Q2 What is "Cross-Run Text Fragmentation" in Word, and how does RapidDoc solve it?
In Microsoft Word's underlying OpenXML (word/document.xml), a sentence is rarely stored as a single continuous string. Word fragments sentences into multiple <w:r> (run) XML elements due to spellchecks, edits, or formatting changes. For example, "Confidential Draft" might be split into three separate run tags: "Conf", "ident", and "ial Draft". A standard find-and-replace algorithm will fail to find "Confidential Draft" because the phrase does not exist inside any individual XML tag.

How we solved it: Inside docx_editor.py, we built a run-coalescing algorithm. It reconstructs the full sentence text across run boundaries while tracking the exact character indices within each XML run node. When a match is found, it splits and merges the runs cleanly, injects the replacement text, preserves surrounding formatting, and adds yellow highlighting (<w:highlight w:val="yellow"/>) for review.
Q3 Why did you build a 3-tier cascade instead of relying 100% on Google Gemini?
Relying entirely on a third-party cloud LLM introduces three major drawbacks:
  1. Cost: Paying per-token fees for simple tasks (like "replace old logo" or "change font to Arial") is financially unsustainable.
  2. Privacy & Offline Access: Enterprise and academic documents often contain confidential data that cannot be sent to third-party cloud servers. Local models run completely offline.
  3. Network & API Latency/Failures: If the cloud API has a network glitch or rate limits, the entire application crashes.

By having Local Brains (Tier 1), Gemini Cloud (Tier 2), and Deterministic Regex Rules (Tier 3), RapidDoc stays fast, private, free to run locally, and achieves 100% uptime.
Q4 How does the Long-Document Summarizer prevent "loss of late sections"?
Most transformer summarizers (like BART) have a maximum token limit of 1,024 tokens (~750 words). In traditional systems, any document longer than 2 pages is blindly truncated at the top, which means the most important sections—the Results, Discussion, and Conclusion—are completely ignored.

RapidDoc's Solution: In document_summarizer.py, we implemented a Hierarchical Map-Reduce Pipeline with Late-Section Retention. The document is split by structural headings. In the Map phase, each section is summarized independently. In the Reduce phase, the section summaries are synthesized into a global summary. Terminal sections (Conclusions and Recommendations) are guaranteed a dedicated allocation in the final output.
Q5 How does RapidDoc generate PowerPoint presentations without content overflowing the slides?
Naively packing paragraphs into slides results in broken, unreadable decks. RapidDoc's ppt_templates.py does three things:
  1. Semantic Outline Parser: Identifies headings up to depth 3 to establish slide boundaries. If headings are missing (common in lab reports), it parses table label columns (e.g., "Objective", "Problem Statement") as implicit headings.
  2. Pre-designed Layout Templates: Applies branded templates (Modern, Corporate, Minimal) with deliberate text-box coordinates.
  3. Overflow Control: Enforces hard limits: maximum 7 bullet points per slide (longer lists automatically spill to a new slide), maximum 14 table rows per slide, and automatic font-scaling to fit bounding boxes.
Q6 How does RapidDoc handle image replacement without hallucinating image indices?
In image_resolver.py, we intentionally avoided using a generative model for image replacement. A prompt like "replace the second image" is an addressing problem, not a perceptual generation problem.

Our rule-based image resolver inspects the document's real image list, extracts ordinal keywords ("first", "2nd", "last"), and verifies that the index actually exists in the file. If there is ambiguity (e.g. "replace the image on page 3" when page 3 has two diagrams), it surfaces both options to the UI rather than making a random guess.
Q7 How does the version history snapshot system work? Why copy files instead of diff patches?
In version_history.py, we capture a Copy-on-Write binary snapshot before every single mutation, maintaining up to 40 reversible versions.

We deliberately chose full binary copies over incremental diff patches because OpenXML files are binary ZIP archives containing interdependent XML parts and media assets. Storing git-style text diffs against binary archives frequently drifts out of sync and corrupts files during rollback. Full copies guarantee 100% reliable one-click rollback to any previous version.
Q8 How do dynamic page numbers work in Word XML?
Unlike plain text where someone writes "Page 1", Microsoft Word uses dynamic XML field codes. In header_footer.py, we inject an OpenXML simple field element (<w:fldSimple w:instr="PAGE"/>) along with NUMPAGES for total pages. This ensures that when the user adds or deletes pages in Microsoft Word or LibreOffice, Word automatically recalculates the page numbers dynamically.
Q9 What role does MongoDB play versus local disk storage?
RapidDoc uses a hybrid storage architecture:
  • MongoDB Community Server (via Motor async driver): Stores structured metadata: user profiles, hashed passwords, document ownership, pipeline progression states (Ingested ➔ Header/Footer ➔ Content ➔ Finalized), and edit logs.
  • Local Disk Storage (/storage): Stores the heavy binary assets: uploaded DOCX/PDF files, extracted image assets, and version snapshots (v1.docx, v2.docx). This keeps MongoDB queries light and fast.
Q10 How does live preview work in the web browser without Microsoft Word installed?
In preview.py and pdf_converter.py, the backend renders the Word document to high-fidelity PDF pages using headless LibreOffice or converts text runs into structured HTML paragraphs. The frontend renders this inside a sandboxed viewport with zoom controls and side-by-side editing, allowing users to see their changes in real-time on any browser and operating system.
